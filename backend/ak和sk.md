AK/SK 是一种常见的**身份认证与鉴权机制**，全称是 **Access Key ID / Secret Access Key**。它本质上是一对密钥，用于证明“你是谁”，常用于 API 调用、云服务、开放平台等场景。

## 1. 基本概念

| 名称                        | 说明                         | 是否保密                               |
| --------------------------- | ---------------------------- | -------------------------------------- |
| **AK**（Access Key ID）     | 公开的身份标识，类似“用户名” | 可以公开，但一般不主动暴露             |
| **SK**（Secret Access Key） | 私密的密钥，类似“密码”       | **必须严格保密**，只存于客户端和服务器 |

> 简单类比：AK 是银行卡号，SK 是银行卡密码 + 签名密钥。

## 2. 为什么需要 AK/SK？

传统的“用户名 + 密码”方式在 API 场景中有几个问题：

- 密码不能每次请求都明文传输
- 无法防止请求被篡改
- 无法防止重放攻击
- 不适合程序自动化调用

AK/SK 机制通过**签名**解决这些问题：客户端用 SK 对请求内容计算签名，服务端用同样的 SK 验证签名。SK 本身**不在网络上传输**。

## 3. 典型鉴权流程

以调用一个云服务 API 为例：

```
客户端                                      服务端
  |                                           |
  |  1. 准备请求（方法、URL、参数、时间戳等）      |
  |                                           |
  |  2. 用 SK 对请求内容计算签名 signature       |
  |                                           |
  |  3. 发送请求：                              |
  |     AK + 时间戳 + 签名 + 请求内容            |
  |  --------------------------------------->  |
  |                                           |
  |                    4. 用 AK 查出对应的 SK    |
  |                    5. 用同样算法重算签名      |
  |                    6. 比对签名是否一致        |
  |                    7. 校验时间戳是否过期      |
  |                                           |
  |  <---------------------------------------  |
  |           返回结果或 401/403                |
```

## 4. 签名通常包含哪些内容？

为了防止篡改和重放，签名一般会覆盖：

- HTTP 方法（GET/POST 等）
- 请求路径和查询参数
- 请求体（Body）的哈希
- 时间戳（防止重放）
- 随机数（Nonce，进一步防重放）
- 部分协议还会加入 Headers

常见算法：**HMAC-SHA256**、**HMAC-SHA1**。

签名伪代码：

```
stringToSign = method + "\n" +
               path + "\n" +
               queryString + "\n" +
               timestamp + "\n" +
               nonce + "\n" +
               sha256(body)

signature = Base64(HMAC-SHA256(SK, stringToSign))
```

请求时带上：

```
AK: AKIDxxxx
Timestamp: 1700000000
Nonce: abc123
Signature: xxxxxxxx
```

服务端用同样的 `stringToSign` 和 SK 重算，一致则通过。

## 5. 安全要点

| 风险        | 防护措施                                            |
| ----------- | --------------------------------------------------- |
| SK 泄露     | 绝不前端明文存储；使用环境变量、密钥管理服务（KMS） |
| 请求被篡改  | 签名覆盖请求关键内容                                |
| 重放攻击    | 时间戳 + Nonce，服务端缓存已用 Nonce                |
| 中间人攻击  | 必须配合 HTTPS                                      |
| SK 长期不变 | 支持轮换、多对 AK/SK、临时凭证（STS）               |
| 权限过大    | 配合 RAM/IAM 做细粒度授权                           |

## 6. AK/SK 与常见方案对比

| 方案         | 特点                        | 适用场景             |
| ------------ | --------------------------- | -------------------- |
| AK/SK 签名   | 无状态、适合服务端对服务端  | 云 API、开放平台     |
| OAuth2       | 授权委托、有 token 生命周期 | 第三方登录、用户授权 |
| JWT          | 自包含、可携带声明          | 前后端分离、微服务   |
| Session      | 服务端存储状态              | 传统 Web             |
| STS 临时凭证 | AK/SK 的临时版本            | 移动端、前端直传     |

## 7. 实际例子

**AWS**：`AWS Access Key ID` + `AWS Secret Access Key`，用 SigV4 签名。  
**阿里云**：`AccessKey ID` + `AccessKey Secret`，用 HMAC-SHA1/SHA256 签名。  
**腾讯云**：`SecretId` + `SecretKey`，用 TC3-HMAC-SHA256 签名。  
**七牛/又拍**：也是 AK/SK 上传鉴权。

## 8. 一句话总结

> **AK 用来告诉服务端“我是谁”，SK 用来证明“我真的是我”，且 SK 永不传输，只用来算签名。**
